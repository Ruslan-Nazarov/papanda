# R3: хранение, миграции и публичные ссылки

## Решение о хранении

Сохраняем SQLite: одна личная БД либо отдельная БД на серверную demo-сессию.
Demo работает одним процессом на DATA_DIR; это обеспечивается файловой блокировкой.
Аккаунты и постоянное многопользовательское хранение с owner_id требуют отдельного
продуктового решения. Произвольная cookie не является доказательством владения
старой demo-базой.

Реестр security.sqlite3 хранит хеш идентификатора сессии, фиксированный expires,
last_seen, квоты и каталог публичных токенов. Активность обновляет last_seen,
но не продлевает семидневный TTL. Публичный читатель не создаёт сессию.

В памяти допускается MAX_CACHED_ENGINES (по умолчанию 32). Вытесняется самый давно
использованный свободный engine с dispose. Если все заняты — 503 с возможностью
повторить запрос. Запросы к одной БД сериализуются; leases учитывают также очередь.
Очистка пропускает занятые БД, освобождает engine, затем удаляет DB/WAL/SHM и
записи реестра. Файловые соединения используют NullPool, что проверено на Windows.

## Версия и миграции

PRAGMA user_version=1 задаёт версию схемы SQLite. Note и Block имеют
schema_version=1; revision документа — целое число от 1. Перед обслуживанием
запросов проверяются личная БД или все существующие зарегистрированные активные
demo-БД. Новая demo-БД инициализируется перед первым запросом к ней.

Миграция 001 поддерживает предыдущую полную схему R2 с user_version=0.
Она проверяет таблицы, поля, PK, FK, целостность и уникальность. Неизвестная
будущая версия, неполная схема, сироты и повреждённый JSON останавливают запуск.
DDL и преобразование содержимого выполняются в одной явной транзакции.
У существующей БД предварительно создаётся проверенный снимок в
DATA_DIR/migration-backups. Повторный запуск версию 1 не меняет.

Существующие допустимые ID блоков сохраняются; отсутствующие/повторные/недопустимые
заменяются детерминированными UUID. История адаптируется тем же правилом.
Статусы блоков draft/done переходят в in_progress/ready. Текст и дополнительные
поля остаются прежними. Начальная загрузка примеров добавляет только отсутствующие
sync_id и не перезаписывает пользовательские изменения.

## Сохранение и API

PATCH требует revision прочитанного документа. Проверка в сервисе и условный UPDATE
SQLAlchemy защищают от устаревших записей, в том числе между соединениями.
Конфликт возвращает 409. UI сохраняет dirty и локальный текст, прекращает
повторный autosave конфликтного документа; ручное сохранение предлагает отдельную
копию. Подтверждение одного сохранения передаёт новую revision следующему запросу.

Отсутствующее поле PATCH не меняется. category_id:null и sticker_text:null очищают
значение; null у обязательных полей даёт 422. Неверные enum/ID/шаги дают 422,
несуществующие категории и стороны связи — 404, дублирование — 409.
Удаление категории увеличивает revision затронутых документов.

Восстановление версии требует текущую revision и сохраняет исходное содержимое
отдельной версией в той же транзакции. Версию можно восстановить/закрепить/удалить
только через ID её собственного документа. История, категории, связи и sharing
вынесены в отдельные сервисы; NotesService сохраняет фасад для текущих роутов.

## Sharing

Ссылка — live view сохранённого содержимого, только чтение. Каталог токенов
разрешает владельца независимо от cookie посетителя; затем проверяются действующая
сессия и токен непосредственно в БД автора. Последняя проверка является источником
прав доступа. Каталог восстанавливается при старте из зарегистрированных БД.

Повторная публикация возвращает прежний токен. Отзыв, перенос в корзину,
окончательное удаление и истечение demo-сессии закрывают доступ. Восстановление
из корзины не восстанавливает старую ссылку. Новая публикация выдаёт новый токен.
Изменение токена не повышает revision текста.

Публичная HTML-страница показывает ручные блоки и секции. HTML очищается перед
выводом; API публикует только заголовок, schema_version и разрешённые поля блоков.
Страницы/API имеют no-store и no-referrer; аналитика на публичной странице
не загружается, чтобы не передавать URL с токеном. Уже полученную читателем копию отозвать
невозможно. Личный режим сохраняет ограничение loopback: для доступа через интернет
нужен поддерживаемый demo-режим.

Запись документа и запись каталога находятся в разных SQLite-файлах. При сбое
между ними ссылка может временно не открываться; повторная публикация или старт
восстанавливают каталог. Устаревшая запись каталога не даёт доступ после отзыва,
поскольку токен повторно проверяется в исходной БД.

## Проверка копии и восстановление

Команды выполняются из корня репозитория. Все пути назначения должны быть новыми:

```powershell
.venv\Scripts\python.exe -m scripts.backup_db data/db/papanda.db backups/before-upgrade.db
.venv\Scripts\python.exe -m scripts.migrate_db_copy backups/before-upgrade.db backups/migrated-copy.db
```

backup_db использует SQLite backup API, integrity_check и пробное восстановление
в память. migrate_db_copy оставляет исходник неизменным; при ошибке копия остаётся
для диагностики. При FK-сиротах сначала применяют repair_db_copy.py к новой копии
с карантином, затем повторяют миграцию. Автоматического удаления проблемных строк нет.

Для отката остановить приложение, сохранить повреждённую БД и её sidecar-файлы,
восстановить проверенную резервную копию в новый файл и указать DATABASE_URL на него.
Для отката к R2 использовать код R2 и снимок до миграции. Возврат к старому коду
на уже изменённых данных не является поддерживаемым downgrade.

Снимки содержат личные данные и не удаляются автоматически по TTL demo.
Оператор управляет их доступом и сроком хранения отдельно.

## Старые незарегистрированные demo-БД

Они не подключаются по старой cookie и не удаляются очисткой. После подтверждения
владельца оператор может перенести копию в новую серверную сессию: получить сессию
через главную страницу, не открывая API конспектов, сохранить её токен в закрытый
локальный файл, остановить demo-сервер и выполнить:

```powershell
$env:DEMO_MODE='true'
.venv\Scripts\python.exe -m scripts.import_legacy_demo backups/legacy.db --session-token-file data/private-session-token.txt
```

Скрипт требует живую выданную сессию, эксклюзивную блокировку и отсутствие БД
назначения; не сливает и не заменяет данные. Копия мигрируется, прежние публичные
токены отзываются, исходник сохраняется. Токен не выводится в журнал. После переноса
удалить закрытый файл токена и запустить demo-сервер. TTL новой сессии не меняется.
В этой работе неизвестные старые demo-файлы пользователя не переносились.
