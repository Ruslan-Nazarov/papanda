# Сохранение заданного процесса в dialectic_v3

Изменение согласовано пользователем 2026-10-08 после двух локальных прогонов
с запросом «Как разработать одноканальный ЭКГ по приложенному ТЗ».
Граница анализа — процесс из запроса, а не автоматически работа его результата.

## Реализация

`fastapi_app/services/generation/scoped_dialectic_builder.py` управляет построением
в приложении поверх блоков пакета `dialectic_world==0.4.0`.
Пакет и его авторские промпты в установленном окружении не изменяются.
Согласованные дополнения находятся в `prompts/engine_scope/*.en.md`.
Исходные определения развития и противоположности пакета сохраняются.

1. `FindP0` получает неизменный запрос и причины содержательных отказов.
   Ответ содержит `analyzed_process` и `subject_preservation`.
2. Отдельный `CheckScope` сопоставляет запрос, документ и кандидата.
   `SUBSTITUTED` возвращает выбор P0 с конкретной причиной;
   `INSUFFICIENT` останавливает построение с частичным результатом;
   `PRESERVED` разрешает развитие, но не подтверждает простейшее окончательно.
3. `CompareDevelopment` дополнительно возвращает `scope_review` и
   `p0_assessment`. Новый P0 выбирается только при содержательном `REJECT`.
   Нарушившая границы итерация сохраняется в трассировке, но исключается
   из принимаемого конспекта. Это останавливает попытку, не отбраковывая P0.
4. Следующая итерация получает замечания сравнения и результаты проверки
   противоположности. История развития передаётся по исходному правилу
   пакета — через целую непосредственно предшествующую итерацию.
5. Предел итераций возвращает `partial` с `iteration_limit`, не инициируя
   автоматическую отбраковку P0. Неопределённые проверки противоположности
   отмечаются причиной `opposition_evidence_insufficient`.

Полный документ продолжает передаваться через `DialecticLLM` в каждый вызов,
включая `CheckScope`. Стабильный префикс документа не изменяется.
Замечания передаются отдельно; JSON проверки каждого кандидата сокращается
до `brief_max_chars`, а её идентификатор и вердикт сохраняются явно.

Результат содержит причину остановки, проверки границ кандидата и последнюю
проверку границ итерации в `report`. Сохранённый `ScopedWorld` дополнительно
содержит архив предыдущих содержательно отклонённых попыток; их разные P0
не объединяются в одну цепочку итогового конспекта.

## Проверка и ограничения

`tests/test_scoped_dialectic_builder.py` проверяет реальный цикл и парсеры
с детерминированными ответами: отказ до развития, передачу замечаний,
сохранение P0 при пределе поиска, исключение непригодных итераций,
отказ при неполном контракте и путь через противоположность к разрешению.
Смысловые вердикты остаются оценками LLM; тесты не доказывают их истинность.

При обновлении версии пакета необходимо сверять используемые API блоков,
схемы ответов и совместимость дополнений к промптам.
Изменение не гарантирует полноту всех требований ТЗ.

## Объяснение и проверка развивающих процессов (2026-10-09)

`generation/development.py` содержит общий для полного конспекта и отдельного
шага 2 вызов `ReviewDevelopment` после `BuildIteration`. Проверка получает
исходный `prompt_2` пакета с тем же P0, полной предыдущей итерацией и контекстом,
а также полный структурированный ответ генератора. Она возвращает отдельный
вердикт и обоснование для каждого процесса: `ACCEPT`, `REJECT` или `UNDETERMINED`.
Необходимость внешнего условия сама по себе не считается доказательством
развития. Проверка не запускает поиск противоположности.

Для принятого процесса тот же вызов составляет связное объяснение из `process`,
`development_relation`, `reveals` и `practical_significance` с учётом `basis`.
Четыре раздела авторского `8_генератор_шага_промпт.md` о механизме, показе,
изложении для читателя и технических ограничениях подключаются дословно.
Старая схема количества процессов и определения из других разделов этого файла
в новый движок не переносятся. Авторские файлы не изменяются.

Если хотя бы один процесс отклонён или недостаточно обоснован, весь кандидат
текущей итерации возвращается генератору вместе с замечаниями на одну попытку
исправления. Это повтор той же итерации, а не следующая итерация развития.
Повторный отказ, ошибка проверки или отмена не добавляют кандидатов в принятый
мир и не возвращают их как карточки. Все вызовы используют общий бюджет запуска.

`ScopedWorld.development_texts` хранит объяснения по внутренним id процессов,
`development_reviews` — вердикты попыток. Исходный структурированный ответ
сохраняется в `IterationRecord.raw` без замены формулировок редакторским текстом.
Отображение использует проверенное объяснение; для старых снимков без него
сохраняет имеющиеся поля объяснения вместо вывода одного `statement`.
Сохранённые ранее конспекты автоматически не переписываются.

Тесты `test_development.py` проверяют сохранность объяснений, повтор с конкретными
замечаниями, отбраковку неполного ответа проверки, отмену и оба пути генерации.
Вердикт остаётся оценкой модели: тесты подтверждают применение проверки,
но не доказывают содержательную истинность каждой будущей генерации.

## Ревью реализации промптов в ручной и полной генерации

По запросу пользователя от 2026-10-09 проверены пути от запроса редактора до
карточек: основной `dialectic_v3` и запасной `legacy`. Исправления сделаны в коде;
авторские файлы промптов и установленный пакет не редактировались.

Основной движок использует `prompt_1.en.md`–`prompt_6.en.md` установленного
`dialectic_world==0.4.0`, дополнения `prompts/engine_scope` и выбранные разделы
`8_генератор_шага_промпт.md` для изложения. Файлы `11_...`–`20_...` принадлежат
запасному движку. Правка одного набора не заменяет другой автоматически.

| Обнаруженное расхождение | Исправление и проверка |
| --- | --- |
| Текст, заголовок и стикеры целевого шага исключались вместе с будущими шагами. | `step_to_revise` передаётся отдельно от предшественников; будущие шаги не попадают в одиночную генерацию. |
| Язык короткого уточнения заменял язык исходного запроса. | Исходный запрос сохраняется; уточнение меняет язык только при явном указании. |
| Снимки движка повторно использовались после замены документа или промптов. | Проверяются подписи источника и промптов, текста, заголовков и стикеров. Старые либо повреждённые снимки уступают видимому тексту. |
| При нескольких подтверждённых противоположностях продолжалась только первая. | `OppositionBranch` сохраняет каждую ветвь; противоречие и разрешение строятся для каждой. Карточки `step3.N`, `step4.N`, `step5.N` сохраняют соответствие. |
| Парсеры принимали утверждения о противоположности и разрешении с пустыми основаниями. | `engine_contracts.py` проверяет поля авторских схем, уникальность ссылок, доказательства замещения и согласованность статусов. REPLACEMENT требует замещения обеих сторон; MEDIATION не подтверждает P0. |
| Сравнение развития принималось по общему выводу без анализа отдельных процессов и межитерационных переходов. | Проверяется полный состав `development_steps`, `relations_to_p0`, `iteration_patterns`, переходов между итерациями и обоснований кандидатов по схеме промпта 3. |
| Вручную заполненный шаг 3 автоматически считался подтверждённым; шаг 4 — сформированным противоречием. | Перед продолжением выполняется проверка предоставленного текста по авторскому промпту. Текст прежних карточек не переписывается. |
| Неопределённость формирования противоречия считалась ошибкой формата с повторным запросом. | Содержательные отрицательные ответы сохраняются в `stage_failures`, возвращается частичный результат, поиск скачка для этой ветви не запускается. |
| Пакет требовал не более шести развивающих процессов, хотя промпт не задаёт это число. | Приложение проверяет непустой конечный список и полную основу каждого процесса; объём ограничивается бюджетом запроса. |
| В шагах 3–5 терялись замещение, путь развития и преобразование содержания обеих сторон. | `presentation.py` получает полные структурированные основания и составляет текст для читателя по авторским правилам изложения. Исходный JSON сохраняется. |
| Успешный отдельный шаг P0 имел общий статус `built`, который можно было принять за подтверждение всего цикла. | Для представления отдельно вычисляется `p0_confirmed`; одно лишь успешное заполнение шага его не устанавливает. |
| В `legacy` одиночная генерация заново планировала весь конспект, не опираясь на реальные предшественники, и удаляла последующие шаги. | `Planner.plan_step` планирует и проверяет только выбранную стадию; заменяется только выбранное семейство карточек. Материалы запроса передаются планированию и валидации. |
| В `legacy` поля «разворачивает» и «обратный_ход» исчезали перед валидацией и последующими стадиями. | Общая сборка списка блоков сохраняет оба поля перехода. |
| Удаление HTML-тегов склеивало абзацы и оставляло HTML-сущности и дубли формул. | `NoteText` извлекает текст через инертный DOM, сохраняет разделение абзацев и исходный LaTeX. Один метод используется для запроса и привязки снимков. |

Разделение ответственности: `note_context.py` — границы контекста и подписи;
`development.py` — развитие и его проверка; `engine_contracts.py` — схемы ответов
и ветви противоположностей; `presentation.py` — изложение сохранённых оснований.
Одиночный и полный режимы используют эти же функции, а не разные реализации
критериев. Завершённые ветви сохраняются и при недостаточности оснований в другой.

Регрессии покрыты `test_prompt_fidelity.py`, тестами движка, API и редактора.
Реальные ответы LLM в этом ревью не запрашивались. Корректность проверок и
сохранность данных подтверждаются тестами; смысловые оценки модели по-прежнему
могут ошибаться. Дополнительная проверка ручных предпосылок и изложение результата
добавляют вызовы модели в пределах общего бюджета генерации.

Итог проверки: 356 серверных тестов прошли, 4 пропущены; 58 тестов интерфейса
и 25 браузерных проверок прошли. Сборка интерфейса, ESLint и проверка типов
завершились успешно. Деплой в рамках ревью не выполнялся.
