# R2: доступ, квоты и внешние данные

Решение от 24.09.2026, ветка `refactor/staged-hardening`.

## Поддерживаемые сценарии

| Режим | Граница доступа | Хранение |
|---|---|---|
| Личный, `DEMO_MODE=false` | Только loopback-клиент и Host localhost/127.0.0.1/::1, без Forwarded-заголовков | Личная SQLite |
| Временная demo, `DEMO_MODE=true` | Случайная cookie как bearer-токен; её SHA-256 проверяется в серверном реестре | Отдельная БД на серверный session ID |
| Приватный сервис с аккаунтами | Пока не поддерживается | Требуются аутентификация и owner_id; отдельная миграция |

Личный режим не предназначен для нескольких пользователей ОС, туннелей или
публикации через reverse proxy. Изменения через браузер дополнительно проверяют
Origin и Sec-Fetch-Site. У локального небраузерного клиента с доступом к loopback
остаётся доступ к личному редактору.

Demo сохраняет отдельные БД до миграции R3: это ограничивает объём текущего
изменения и позволяет проверить изоляцию заметок, версий, категорий и связей.
Cookie не содержит выбираемый пользователем путь/ID БД. Секретный токен существует
только в cookie; в `data/security.sqlite3` хранится его хеш и срок действия.
Потеря cookie означает потерю доступа к временной сессии. Это не учётная запись.

Срок сессии фиксирован при создании: 7 дней, максимум 1000 записей реестра.
Просроченная сессия не обслуживает запросы. Раз в час удаляются её зарегистрированные
БД/WAL/SHM после закрытия engine; активная операция откладывает удаление.
Режим demo допускает **один процесс на DATA_DIR**, что обеспечивается файловой
блокировкой на старте. Для файловой SQLite используется NullPool, соединения
не остаются открытыми между запросами.

Старые cookie не переносятся в новый реестр; неизвестные старые demo-БД остаются
на диске и автоматической очисткой не затрагиваются. Перед публичным выпуском
нужна отдельная процедура переноса/удаления старых demo-данных. Личная БД сохраняется.
Публичные ссылки между demo-сессиями и показ всех ручных блоков — оставшаяся работа R3.

## Квоты и доверие к прокси

Суточный допуск к generate-full/generate-step резервируется одной транзакцией
SQLite `BEGIN IMMEDIATE`: общий лимит 3000, сессия 40, IP 80 (UTC).
Отказ в любом лимите откатывает всю резервацию; начавшаяся неудачная генерация
расходует её. Рестарт процесса не сбрасывает счётчики. Это число операций,
не бюджет токенов/внутренних вызовов — последний относится к R4.
Очистка cookie не обходит IP- и общий лимиты; несколько IP всё ещё делят общий лимит.

Перед записью demo проверяется занятый объём SQLite (page_count минус freelist),
порог 32 МиБ. Чтение и DELETE доступны после порога; освобождённые страницы
снова учитываются как доступные. Это порог допуска операции: итоговая запись,
индексы, параллельные операции и WAL могут превышать порог. Для жёсткого лимита
диска при размещении нужен лимит файловой системы/контейнера.

По умолчанию Forwarded-заголовкам нет доверия. Для nginx на том же узле:

```dotenv
DEMO_MODE=true
TRUSTED_PROXY_COUNT=1
TRUSTED_PROXY_IPS=127.0.0.1/32,::1/128
```

Uvicorn запускать с `--no-proxy-headers` (`run.py` уже задаёт это), иначе приложение
не увидит настоящий socket peer. Nginx должен передавать Host, заменять
X-Forwarded-Proto и добавлять адрес клиента в X-Forwarded-For. Backend слушает
loopback; прямой внешний доступ к нему закрыт. Доверяются только заданные IP/CIDR
и проверенная цепочка прокси. HTTPS-схема от такого прокси даёт Secure cookie
и корректную проверку Origin. Публичная demo требует HTTPS.

## Импорт

- Всё HTTP-тело ограничено 12 МиБ и 20 секундами чтения, включая chunked и multipart.
- Файл — до 8 МиБ; чтение ограничивается повторно внутри обработчика.
- PDF — до 50 страниц, отдельный процесс, 15 секунд, 512 МиБ памяти, два процесса
  одновременно; ожидание свободного места до 1 секунды, затем 429.
- Ограничение памяти: Windows Job Object, Linux RLIMIT_AS. При невозможности
  применить ограничение worker завершается с ошибкой; это изоляция ресурсов,
  а не полноценная песочница от исполнения произвольного кода.
- Worker не получает ключи провайдеров в окружении; передаёт не более 15000 символов
  извлечённого текста. Повреждённые, зашифрованные PDF и превышение страниц дают 400,
  таймаут — 408, превышение байтов — 413. По таймауту/отмене процесс завершается.
- URL — только http(s), порты 80/443, без userinfo. Проверяются все DNS-адреса
  каждого редиректа, соединение устанавливается с проверенным IP. Host и TLS SNI
  сохраняют исходное имя; [механизм httpcore](https://www.encode.io/httpcore/extensions/#sni_hostname).
- URL: до 2 МиБ, четырёх запросов и 20 секунд суммарно. Запрашивается identity;
  если сервер всё равно прислал сжатый ответ, он отклоняется до распаковки.
  Переменные HTTP_PROXY/HTTPS_PROXY для импорта не используются.

## GigaChat TLS

OAuth и API используют один проверяющий SSLContext. `GIGACHAT_VERIFY_SSL=false`
теперь вызывает ошибку конфигурации. CA задаётся только для клиента GigaChat;
системное хранилище и certifi не меняются.

```powershell
.\.venv\Scripts\python.exe scripts\download_gigachat_ca.py
.\.venv\Scripts\python.exe scripts\check_gigachat_tls.py --ca data/certs/russian_trusted_root_ca.pem
```

Скрипт скачивает CA по проверяемому HTTPS с адреса из
[официальной инструкции GigaChat](https://developers.sber.ru/docs/ru/gigachat/certificates).
Файл назначения не перезаписывается. После проверки указать в `.env`:

```dotenv
GIGACHAT_VERIFY_SSL=true
GIGACHAT_CA_BUNDLE=data/certs/russian_trusted_root_ca.pem
```

В локальном окружении это выполнено. SHA-256 файла CA:
`936a43fea6e8e525bcc0f81acd9c3d21b4fc4b9b68acea7906d698005afc6504`.
Проверены TLS-соединения с OAuth:9443 и API:443 без отправки ключей и генерации.
Тест с локальным недоверенным сертификатом подтверждает отказ в соединении.
