# R4: контракт генерации

## Операция и результат

JSON и SSE используют один Orchestrator. `GenerationContext` хранит run_id,
source_revision, текущий план, свежие тексты, общий дедлайн и журнал физических
LLM-вызовов. Генерация работает с копией входных данных; запись в БД происходит
через обычное сохранение редактора с revision/409.

| Статус | Значение |
|---|---|
| completed | Все запрошенные блоки получены; полный конспект прошёл Judge |
| partial | Есть текст, но операция оборвалась или Judge не подтвердил результат |
| failed | Запрошенные новые блоки получить не удалось |
| cancelled | Операция отменена; после disconnect передать terminal клиенту уже нельзя |
| not_applicable | Планировщик отклонил применимость до текстовых вызовов |

Одиночный шаг — завершённый **черновик** (`in_progress`): его status может быть
completed, но judge остаётся unavailable, поскольку весь конспект не оценивался.
Статусы Judge — passed/failed/unavailable — всегда отдельны от статуса операции.
Недоступность сети, неправильный JSON, строковые boolean и противоречивые поля
оценки не становятся passed.

## Компоненты

- Planner: пять стадий со строгими DTO и отдельной проверкой каждой стадии;
  проверка уникальности ID, существования родителей и отсутствия циклов.
- TextGenerator: последовательная генерация в порядке зависимостей; получает
  свежие предыдущие тексты. Вопрос к шагу содержит и его исходный текст.
- Judge: строгий JSON-объект, независимая оценка по фактической модели.
- RepairPolicy: замечание и текущий текст передаются в исправление; изменённый
  шаг и последующие зависимые шаги обновляются последовательно. Неудачный
  простейший процесс требует нового плана.
- ProviderAdapter: завершение SDK, расход, дедлайн и явный обрыв/пустой ответ.
- Transport: единый конверт событий и отмена при отключении HTTP-клиента.

Сохраняется максимум двух общих попыток, двух планов внутри попытки и двух
попыток каждой стадии. Общие лимиты могут прервать работу раньше.
`use_skeleton` временно оставлен для совместимости внутренних вызовов:
непроверенный путь без плана больше не используется.

## Провайдеры и лимиты

`RoutePolicy.preferred` задаёт порядок, `allowed` — допустимый набор.
Fallback не выходит за allowed. Исключение модели действует до запроса и
проверяется по `response.model` после ответа. Нормализуются известные формы
`openai/<model>` и `<model>:free`; неизвестные алиасы разных провайдеров нельзя
автоматически доказать эквивалентными. При добавлении алиаса нужна проверка.

Для независимой проверки нужны доступные разные модели. Один настроенный
провайдер с одной моделью может оказаться недостаточным: проверка плана завершится
ошибкой, финальный судья — unavailable. Fallback на ту же известную модель через
другой сервис независимостью не считается.

| Настройка | По умолчанию |
|---|---:|
| GENERATION_TIMEOUT | 300 секунд, включая ожидание очереди, RAG, retry и backoff |
| GENERATION_MAX_CALLS | 60 физических LLM-вызовов |
| GENERATION_MAX_TOKENS | 1 500 000 единиц консервативного резервирования |
| GENERATION_CONCURRENCY | 2 операции на процесс |

Перед каждым запросом резервируются UTF-8 байты сериализованных сообщений,
накладные расходы и запрошенный максимум output tokens. Резерв не возвращается
после ошибки; format fallback и retry расходуют новый резерв. Это ограничитель
нагрузки, не точный токенизатор и не финансовая квота. Фактическое SDK total_tokens
учитывается отдельно; `usage_complete=false` означает неизвестный расход хотя бы
одного вызова. Отсутствующие usage не следует считать нулевой стоимостью.

OAuth и справочные HTTP-запросы входят во временной предел, но не в счётчик
LLM-вызовов. Уже принятый удалённым провайдером запрос может тарифицироваться и
после локальной отмены. Ограничение параллелизма действует на процесс; приложение
по-прежнему рассчитано на один worker.

## SSE и применение в редакторе

Каждое событие содержит `type`, `run_id`, `sequence` (строго с 1). Первое —
started, последнее — terminal со статусом и результатом. Поток конспекта сообщает
фазы, затем итоговые блоки и результат; редактор применяет только итоговый набор.
EOF без terminal, повтор terminal, смена run_id и пропуск sequence — ошибка.
Для обычного потока текста fallback разрешён только до первого фрагмента.
Кэш заполняется после корректного полного завершения провайдера.

`replace_bases` задаёт заменяемые семейства: `step2.1/step2.2 → step2` удаляет
оба старых блока. Перегенерация отдельного шага инвалидирует последующие шаги.
Новая структура строится отдельно и применяется одной операцией с dirty/revision.
Перед применением сверяются документ, локальный счётчик правок и server revision.
При конфликте можно сохранить результат отдельной копией; исходные ручные правки
остаются. Partial требует явного согласия применить черновик. Переход на другую
заметку и кнопка отмены прерывают запрос.

Прокси должен допускать длительные SSE-ответы в пределах общего дедлайна:
между статусами возможны длительные запросы к модели. Полный browser E2E и
настройка выпуска остаются этапам R5/R6.

## Проверки и измерения

Контрактные тесты воспроизводят отказ применимости, timeout, rate limit,
неправильный JSON, пустой ответ, обрыв после первого фрагмента, отмену,
точечное исправление и соблюдение общего бюджета. JS-тесты проверяют атомарность,
поздние ответы, ручные правки, отмену и SSE-протокол.

Повторяемый офлайн-набор (8 сценариев × 10 прогонов):

```powershell
.venv\Scripts\python.exe scripts/benchmark_generation.py --output docs/benchmarks/r4-generation-2026-09-24.json
```

В [отчёте](benchmarks/r4-generation-2026-09-24.json) — p50/p95, число запросов,
резерв и искусственный SDK usage. Провайдеры заменены контролируемыми ответами,
задержка каждого — 2 мс (точность зависит от планировщика Windows), usage —
200 токенов на ответ. **Это не замер скорости, цены или качества реальных LLM.**
Успешный полный проход — 18 запросов; при отказе применимости — 1;
с одним rate limit и успешным fallback — 19. Авторские файлы prompts не менялись.
